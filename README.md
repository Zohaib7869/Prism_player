# Prism Player

A premium, offline-first video + audio media player for Android, built in Flutter.

This project was generated by Claude (Anthropic) against a detailed feature spec. It is a
**real, from-scratch Flutter + native-Kotlin codebase** — not a mockup — but it has **not been
compiled or run**. The sandbox this was built in has no network access to `pub.dev` or the
Flutter SDK, so `flutter pub get` / `flutter analyze` / `flutter build apk` were never executed
against it. Treat this as a strong, carefully-reviewed first draft that needs one real build-and-
fix pass in an actual Flutter environment, not a finished, shipped app.

This document is the single place that says, plainly, what's solid and what isn't.

---

## 1. Getting it building

```bash
flutter pub get
flutter analyze
flutter build apk --debug   # try debug first — faster feedback loop than --release
```

Expect the first `flutter analyze` to surface a handful of real issues — type mismatches,
a renamed plugin API, a missing null check — that a static review (which is all that was
possible here) cannot catch the way a real compiler does. See §6 for the specific spots most
likely to need a fix.

You will need:
- Flutter 3.19+ / Dart 3.3+ (the SDK constraint in `pubspec.yaml`)
- Android SDK with `compileSdk 34`, `minSdk 23`
- A real device or emulator with **Android 6.0 (API 23) or newer**; media-heavy features
  (background playback, notification controls, equalizer) are much easier to sanity-check on a
  real device than an emulator

## 2. What's genuinely implemented (not stubbed)

- **Native Kotlin, real implementations, not fakes:**
  - `AudioEffectsPlugin.kt` — Equalizer / BassBoost / Virtualizer / LoudnessEnhancer via
    `android.media.audiofx`, attached to a live Android audio session id
  - `AudioExtractionPlugin.kt` — "Save as Audio" via `MediaExtractor`/`MediaMuxer`, doing a real
    compressed-stream copy of the audio track into an `.m4a` container (see §5 for its real
    codec limitation)
  - `MediaScannerPlugin.kt` — real `MediaStore` queries for video/audio, with incremental
    scanning via a stored watermark timestamp
  - `SafeStorageBridgePlugin.kt` — rename/delete/rescan via `MediaScannerConnection`, native
    video thumbnail generation via `MediaMetadataRetriever`, and album-art byte resolution for
    `content://` URIs (needed because `Image.file` can't read `content://` directly)
- **Global player architecture**: a single `GlobalPlayerController` unifies `video_player`
  (video) and `just_audio` + `audio_service` (audio, background playback, notification
  controls) behind one Riverpod state object, with real Play-as-Audio / Play-as-Video mode
  switching that preserves position, a real queue with repeat/shuffle, and periodic progress
  persistence to Hive.
- **Database**: Hive with hand-written `TypeAdapter`s (no `build_runner` codegen — this sandbox
  couldn't run it, so adapters are written by hand and need to stay in sync with their models by
  hand too if you change a model's fields).
- **Safe Media**: PIN is never stored in plaintext — only a salted SHA-256 hash, in
  `flutter_secure_storage`. Biometric unlock via `local_auth`. Hidden items are a metadata flag,
  never a file move/rename.
- **Theming**: 6 real themes (Midnight, AMOLED, Ocean, Purple, Light, Custom-accent) via a
  centralized `ThemeExtension`, persisted, with every screen reading colors from it — no
  hard-coded colors in feature code.
- **Subtitles**: a real, from-scratch SRT/VTT parser, plus a best-effort ASS/SSA plain-text
  extractor (dialogue + timing only — see §5). Auto-detects a sibling subtitle file by basename,
  or load one manually via `file_picker`.
- Every screen in the spec exists and is wired to real data: Home, Videos, Music (with
  Artist/Album/Genre grouping), Folders, full Video Player (gestures, speed, aspect ratio,
  subtitles, lock, fullscreen), full Audio Player (queue, repeat/shuffle, speed), Playlists
  (+ 3 live-computed smart playlists: Favorites / Recently Played / Most Played), unified
  Favorites, Safe Media vault, Equalizer, global Search, and all 7 Settings subpages.

## 3. Project layout

```
lib/
  core/            theme, database (Hive), services (player, scanner, equalizer, extraction),
                   permissions, secure storage, reusable widgets
  features/        one folder per screen area (home, videos, audio, folders, player,
                   playlists, favorites, safe_media, equalizer, search, settings)
  models/          Hive models (hand-written TypeAdapters) + plain computed models
  repositories/    the only layer that touches Hive boxes directly
  providers/       Riverpod wiring (services/repositories as singletons)
  routes/          go_router config (StatefulShellRoute bottom-nav shell)
android/
  app/src/main/kotlin/com/prismplayer/app/   the 4 native plugins described above
```

`MediaRepository`, `PlaylistRepository`, `SettingsRepository`, `SafeMediaRepository`, and
`EqSettingsRepository` are the only classes that call `Hive.box(...)` directly — screens go
through them. Reactivity to Hive changes is done with `Box.listenable()` + `AnimatedBuilder`
directly in each screen (not a global "revision counter"), which is the idiomatic Hive+Flutter
pattern and keeps re-renders scoped to the screen that actually needs them.

## 4. Package/app identity

- App name: **Prism Player**
- Android package: `com.prismplayer.app`
- If you rename the package, update it in **four** places: `android/app/build.gradle`
  (`namespace` + `applicationId`), `AndroidManifest.xml` (`android:name` values reference it
  implicitly via the namespace), every `package com.prismplayer.app` line in the four Kotlin
  files, and the `MethodChannel`/`EventChannel` name strings in
  `lib/core/services/*_service.dart` (they're hard-coded strings like
  `'com.prismplayer.app/audio_effects'` on both the Dart and Kotlin sides — these must match
  exactly, renaming the package alone won't update them).

## 5. Deliberately, honestly scoped-down (not faked)

These are real platform constraints, not laziness — each one is called out in a code comment at
the exact spot it matters, so you're not discovering them by surprise:

- **Multi audio-track switching in video.** `video_player`'s public API doesn't expose ExoPlayer's
  track selection. The "Audio track" menu entry exists (per the spec) but explains this instead
  of pretending to switch tracks. Fixing this for real means replacing `video_player` with a
  custom ExoPlayer + `Texture` platform view — a substantial native undertaking, not a quick
  patch.
- **Equalizer / Volume Booster during native video playback.** `video_player` doesn't expose an
  Android audio session id, and native `AudioEffects` (Equalizer, BassBoost, LoudnessEnhancer)
  need one to attach to. These features work fully during Music playback and "Play as Audio" —
  the Volume Booster sheet and Equalizer screen both say so in-UI rather than silently no-op'ing.
- **"Save as Audio" codec support.** The extraction is a genuine `MediaExtractor`/`MediaMuxer`
  stream copy — no re-encoding. That means it works for the overwhelmingly common case (AAC audio
  in MP4/MKV/MOV/3GP/TS), and fails with a clear, specific error message for anything else (e.g.
  Vorbis-in-WebM). A full transcode pipeline (decode → re-encode to AAC) would remove this
  limitation but is a meaningfully larger feature.
- **ASS/SSA subtitles** get dialogue text + timing, with override tags like `{\an8}` stripped —
  not full ASS styling/positioning/animation. That's a small rendering engine in its own right.
- **Audio normalization** (loudness matching across tracks) is not implemented.
- **Mixed video+audio playlists** don't currently auto-advance across a video→song boundary in
  sequence — `GlobalPlayerController` plays a same-type run (all-video or all-audio) from a
  playlist's contents starting at the tapped item; see `PlaylistDetailScreen._playAt`. Fully
  solving this means either giving the controller a heterogeneous queue concept or transparently
  hopping between the video and audio engines mid-queue.

## 6. Spots to check first if the build fails

Ranked roughly by likelihood of needing a tweak:

1. **`volume_controller` and `screen_brightness` API surface** (`video_player_screen.dart`,
   `_onBrightnessDelta` / `_onVolumeDelta`). Both packages have changed their public API across
   major versions and this sandbox had no way to confirm the exact method names against the
   versions `pub get` actually resolves. Flagged in a code comment at the call site.
2. **`audio_service` / `just_audio` API drift.** `audio_playback_handler.dart` follows the
   well-established official example pattern closely, but pin exact versions
   (`audio_service: 0.18.15`, `just_audio: 0.9.40`) if you hit signature mismatches, rather than
   letting them float to a newer major version first.
3. **Hive adapter drift.** If you add/reorder fields on any model in `lib/models/`, you must
   update its hand-written `TypeAdapter` (`read`/`write`) to match — nothing generates this for
   you here.
4. **`getExternalStorageDirectory()` nullability** (`save_as_audio_dialog.dart`) — force-unwrapped
   with `!`; on the vast majority of real Android devices this is non-null, but it's worth a
   defensive check if you see a crash there on a specific device.
5. **Gradle/AGP/Kotlin version pins** in `android/build.gradle` /
   `android/settings.gradle` (AGP 8.3.2, Kotlin 1.9.24, Gradle 8.6) — these were current as of
   this model's training data but Android tooling moves fast; bump if `flutter pub get`'s Gradle
   sync complains.
6. **`youtube_explode_dart` 2.5.x API surface** (`youtube_service.dart`). Bumped from `^2.3.9` —
   YouTube playback on that pinned version was being throttled to a crawl because it predates
   several `2.4.x`/`2.5.x` signature-deciphering fixes; 2.5.3 is the newest release that still
   works without a bundled `deno` binary (`3.0.0+` requires one for its JS signature solver,
   which isn't viable to ship on a phone — do not bump past `2.5.x` for that reason). The new
   `getQualityOptions`/`getCaptionTracks`/`getCaptionCues` methods use
   `VideoStreamInfo.videoQualityLabel` and `ClosedCaptionManifest.tracks` — these are correct
   as of this library's documented API shape but, like everything in this list, weren't checked
   against a live `pub get` in this sandbox. If `videoQualityLabel` doesn't resolve, the fallback
   is deriving a label from `.videoQuality`/`.videoResolution` instead.

## 7. Bugs found and fixed during self-review

Before this README was written, a systematic (scripted, not just eyeballed) review pass caught
and fixed several real bugs — documented here so the fixes aren't a mystery later:

- A `VideoPlayerController` leak on skip-next/previous (the old controller was never disposed).
- A disposed controller being left referenced in state after a failed video load, which would
  have crashed the next UI build.
- Silent resume-position loss specifically for videos played via "Play as Audio" (wrong
  conditional in the progress-save path).
- Two real missing imports (`PlaybackMode` used without importing its defining file — Dart
  imports are not transitive, so this would have been a compile error).
- A latent class-name collision: this codebase's own action-menu class was originally also
  called `MediaAction`, which collides with a real enum of the same name in the `audio_service`
  package. Renamed to `SheetAction` everywhere before it could bite someone.
- A native Kotlin crash risk: `MediaFormat.getLong(key, default)` is Android API 29+, but the app
  declares `minSdk 23` — fixed to a version-safe try/catch.

## 8. Everything else

Standard error handling throughout: corrupt/unsupported media shows a message instead of
crashing, permission denial is handled gracefully, deleted files don't take down a screen.
Accessibility got standard Material widget semantics for free but wasn't separately audited.
Tablet/landscape layouts use the same responsive widgets as phone but weren't tested against a
tablet-sized viewport (nothing here, was, since none of it has run yet).

## Changelog — this revision

### YouTube playback fix (streams stuck on "loading")

Search worked but tapping a result span the loading spinner forever. Three
things were wrong, in descending order of blame:

1. **`youtube_explode_dart` 2.5.3 was too old.** Its default extraction client
   sends an `androidSdkVersion` field, which trips YouTube's proof-of-origin
   token requirement — audio-only streams come back 403 while muxed streams
   still work. Since `resolveStreamUrl()` picks adaptive (video-only +
   audio-only) for anything at or above 720p, virtually every playback attempt
   hit the 403 path. Bumped to `^3.1.0`, whose default client is
   `androidSdkless`. The 403 was invisible to Dart: `player.open()` had already
   returned, so libmpv just retried in silence.
2. **The `VideoController` was created after `player.open()`.** media_kit boots
   libmpv with `vid=no` and only flips it to `vid=auto` when a controller
   attaches, so the stream was being demuxed with video decoding switched off.
   It is now attached first.
3. **`http-header-fields` was set with `\r\n` as the separator.** mpv parses
   that option's string form as a *comma* separated list, and the user-agent
   string contains a comma (`(KHTML, like Gecko)`), so the header was malformed.
   The user-agent now goes through mpv's dedicated `user-agent` option, which
   also covers the external audio track — that track does not inherit the
   `Media`'s per-item headers, which is what the broken global set was trying
   to work around.

Defence in depth was added on top, because YouTube breaks scrapers routinely
and the failure mode should never again be a spinner with no way out:

- `resolveStreamUrl()` probes both halves of an adaptive pair with a two-byte
  range request before handing them to the player, and falls back to muxed
  360p if either is unauthorized. Worst case the app plays at lower quality
  instead of hanging.
- `getQualityOptions()` hides adaptive picks the probe already rejected, so the
  quality sheet can't drop the user back into the frozen state.
- A 25-second watchdog in `_startRemoteVideo` surfaces a real error if neither
  a position nor a duration ever arrives.
- mpv logs are enabled in debug builds (`logLevel: info`) — filter logcat on
  `[mpv` or `[youtube]` to see the actual status code.
- ProGuard keeps for media_kit's JNI-reached classes, without which remote
  playback fails silently in release builds only.

### YouTube downloads

New feature: pick a resolution or an audio track and download it, with an
in-app library of what's been saved.

**Where the speed comes from.** YouTube shapes each individual connection to
roughly the video's own bitrate, so a single socket downloads a 40-minute
1080p video in about the time it takes to watch it. `SegmentedDownloader`
opens six connections on six different byte ranges, each shaped separately.
Each writes to its own `.partN` file, which makes resume fall out for free —
the bytes on disk *are* the progress record, so a dead network or a killed
process picks up at the exact offset. The parts are concatenated only once
every range completes.

**How 720p+ is assembled.** YouTube stops publishing combined streams above
360p, so higher resolutions are a video-only track that must be paired with a
separate audio-only one. `MediaMuxPlugin` does that with MediaExtractor +
MediaMuxer — a genuine stream copy, no decode/re-encode. An hour of 1080p
merges in seconds with no quality loss.

**Two deliberate limitations:**

- *Audio downloads are `.m4a`, not `.mp3`.* Android ships no MP3 encoder (only
  a decoder), so real MP3 would mean bundling ffmpeg or LAME — tens of
  megabytes of APK and minutes of CPU per file. YouTube's audio-only streams
  are already AAC, so saving them as `.m4a` is instant, lossless, and playable
  everywhere.
- *Video tops out at 1080p.* MediaMuxer's MP4 output accepts only H.264/H.265
  video and AAC audio. YouTube publishes 1440p and 2160p as VP9/AV1 in WebM,
  which would need a real transcode, so the download sheet lists mp4 streams
  only.

**Storage.** Files land in
`Android/data/com.prismplayer.app/files/Prism Downloads/{Video,Audio}`. The
public Downloads folder is avoided on purpose: writing there on Android 11+
needs either MediaStore plumbing or the All-Files-Access permission, which Play
review treats as a red flag. The app-specific directory needs no runtime
permission, and the in-app Downloads screen is the browsing surface anyway.

**Distribution note.** Google Play does not permit apps that download YouTube
content — this is why SnapTube ships as a sideloaded APK rather than through
the Play Store. This feature will cause a rejection if the app is submitted
there. It is not an issue for personal or sideloaded builds.
